# 发布检查清单

## 仓库门禁

- [x] 项目所有者已确认许可证：Apache-2.0。
- [ ] `README.md` 的最小配置、`zcf/application.yml` 的最小安全配置和 `docs/configuration/` 的各模式全量 YAML 与代码字段、默认值及约束一致。
- [ ] CI 在干净的 Linux runner 上通过。
- [ ] 发布跟踪内容不包含测试目录、测试脚本、示例目录、条件测试模块、独立测试报告文件或本地基准输出。
- [ ] 仓库不包含固定测试密码、私网主机、本地绝对路径、私有 registry 配置或同级路径依赖。
- [ ] 用户文档、YAML 注释和发布说明不包含项目约定的违禁词。
- [ ] 新增 HA 管理入口或外部副作用路径时已复用运行代退休门禁；产品适配器的多命令序列全部经过共享有效性令牌保护，并在 `tests/` 下有退休竞态回归。
- [ ] `README.md`“验证”章节列出的格式、编译、静态检查和文档门禁均通过。

## 基础数据面门禁

- [ ] standalone、cluster 和 cluster-node-proxy 的读写、认证、pipeline 保序与管理接口行为符合命令矩阵。
- [ ] 各代理模式的 `read_only` 行为符合命令矩阵：写命令和所有脚本执行路径被拒绝，允许的脚本元数据查询保持可用。
- [ ] 压测前后数据源均已清理并核对，性能结果不存在历史数据污染。
- [ ] 持续负载下 CPU、内存、文件描述符、连接数和待响应缓冲保持在配置边界内。

## 托管复制 HA 门禁

- [ ] replication-ha 白名单产品的主从探测、保护态、人工切换、自动切换和故障注入通过。
- [ ] 主故障达到阈值后，在自动切主等待、租约争用、`auto_failover=false` 和 observer 分支都保持 `protected`，`/ready` 不误报可用。
- [ ] 唯一新主只有在旧主明确跟随、协调结果已提交，或被动模式同时满足“旧主确认宕机 + 同一接管者连续稳定阈值”时才采用；自动切主模式不能借受限跟随绕过 fencing 与协调门禁。
- [ ] observer 在主故障、未确认新主和双主场景均零后端控制写；旁路只读入口另行验证 `read_only=true`。
- [ ] 多主观测立即关闭路由；旧协调模式取得并逐步骤复验租约后才能修复，任何降级失败或权威丢失都不得重新开放。
- [ ] 本轮确认的额外 master 在动作复验时不可达或角色 Unknown 后，风险记录跨 tick 保留；后续仅看到 current 不得开放路由。风险成员经完整证据成为新 current 时只清除自身，其余缺席风险继续在统一 Serving 门禁阻止开放，直到确认成为 replica，或由权威仍有效的 `external-command` fencing 成功证明已物理隔离；`manual` fence 不得清除风险。
- [ ] observer 观测多主后执行同样的纯本地风险记账；额外 master 对 observer 隐藏期间持续 `protected`，且后端角色/复制控制写计数保持为零。
- [ ] 未确认额外 master 保护期间，删除或替换该 HA 运行代的配置事务必须在任何预提交副作用前拒绝；同时禁止用进程重启或滚动发布清空内存证据，维护前保存状态输出，并在独立控制面确认所有已报告 master 已隔离或降级。
- [ ] 多主降级或自动收敛失败进入修复退避，退避窗口内 fencing 与后端控制命令计数都不继续增长。
- [ ] 探测循环不追赶补跑错过的 tick，故障阈值与受限接管的连续轮数保持真实时间间隔。
- [ ] `proxy-cluster` 在“候选已提升、结果未提交”故障注入后以保护态重启，并通过观察票、fencing 和 `CompleteAction` 恢复；不得启动失败或直接采信真实新主。
- [ ] `proxy-cluster` promotion 候选始终等于动作令牌绑定目标；目标在复验时缺席或不合格必须在后端写入前失败。
- [ ] 人工 `failover`/`switchover`/`promote`/`replicaof`/`fence` 在每个外部副作前后复验租约或动作令牌；人工 `promote` 的 fencing 失败时提主命令计数保持为零。
- [ ] 产品适配器多命令切换在每条角色/复制写命令与等待循环中复验动作权威；旧协调 outcome/`CompleteAction` 必须早于本地 `Serving` 发布。
- [ ] 长时间 external fencing 执行中注入租约/动作令牌丢失，NARIX 必须进入保护并终止直接子进程；隔离执行器同时按动作令牌拒绝已过期的后台任务。
- [ ] Redis、Valkey、Redict、KeyDB 与 Dragonfly 的动态持久化责任交接通过；Kvrocks 保持各节点 RocksDB/WAL 且 `ha.persistence.enabled=false`。
- [ ] 外部四层入口后的多代理链路在领导切换期间不会产生双主路由。
- [ ] Redis 租约模式使用真实独立协调器完成租约丢失、续约失败和结果收敛验证。
- [ ] 双节点模式完成 2/2 提交、断链保护、任期恢复和协议不可变验证。
- [ ] 三节点模式完成单成员故障继续提交、失去多数派停止提交和旧令牌拒绝验证。

## 持久化拓扑门禁

- [ ] “1 主 + 1 热备 + 至少 1 快照”拓扑的分配、故障切换、重新加入和持久化责任交接通过。
- [ ] `fail_closed=true` 启动时，在首次 owner 配置写、checkpoint 或验证仍阻塞期间保持 `protected`；验证完成前不得短暂发布 `Serving`。
- [ ] 新 owner 验证后若旧 owner 停用失败，本地 `persistence.owner` 仍保持上一版且 `fail_closed=true` 持续保护；修复后才发布新 owner。
- [ ] 上一版已知 owner 不可达时不得假定其已停用；节点恢复但不再合格后，必须先确认 non-owner 配置再发布新拓扑。
- [ ] Redis 系/Dragonfly 多配置修改在中途失败时恢复调用前配置，租约或动作令牌中途失效后不再发送下一条配置写。
- [ ] 已发布持久化配置被外部改写后能在下一轮重新发现并收敛；本地拓扑缓存不得掩盖后端漂移。
- [ ] 已验证 owner 在最近成功探测宽限内短暂缺席时保持 Serving 且不发送 `REPLICAOF`；宽限耗尽后重新进入严格复验。
- [ ] `force_checkpoint_on_handoff=true` 的旧协调进程重启会重新验证 checkpoint；`proxy-cluster` 跟随者不会采纳未完成 `CompleteAction` 的中间态，且提交指纹覆盖全部 owner、角色与复制链路。
- [ ] 持久化 fail-closed 期间即使多主修复或主节点恢复成功也不提前开放 Serving，只有持久化重新验证后才恢复。
- [ ] 删除 HA 代理、退出 `replication-ha`、关闭持久化或删除 owner 节点前完成后端责任停用；任一已知节点不可达时配置事务必须拒绝。
- [ ] 只有 1 个健康从节点时自动退化为“1 主 + 1 快照”，恢复第二个合格从节点后重新建立独立热备。
- [ ] 新快照责任节点验证失败时不会关闭旧责任节点，失败关闭策略符合配置。
- [ ] 持久化交接与故障切换同时发生时仍只有一个活动协调动作。

## 多 KV 门禁

- [ ] README 的固定后端版本、模式准入和已验证范围与本次发布实际执行的原生命令账本及拓扑门禁一致。
- [ ] 每个固定版本的原生命令账本零未执行，后端原生差异与 NARIX 缺陷分开归档。
- [ ] `backend_profile` 的 RESP、握手和拓扑准入与程序能力表一致。
- [ ] Pika/Codis 等非标准槽位接口未被误写为标准 Cluster 模式。

## 部署门禁

- [ ] 已配置管理端 token。
- [ ] 至少配置一个 `proxies[]` 项；`zcf/application.yml` 中的 `proxies: []` 仅是安全兜底，不能单独作为可运行的业务配置。
- [ ] 业务监听器未在缺少预期前端认证的情况下对外暴露。
- [ ] 只读环境已显式配置 `read_only=true`。
- [ ] 已按代理项合理配置 `max_connections`、pipeline 连接池限制、DedicatedTunnel 限制和超时。
- [ ] replication-ha 自动故障切换按部署形态核对：单实例确认同一组后端只有一个 NARIX 进程在线（进程重叠场景已改配 `local-file` 协调器）；多实例确认 `proxy-cluster` 或 `redis` 协调器已配置；需要零脑裂窗口的场景确认 `fencing.mode=external-command` 及隔离脚本可用。
